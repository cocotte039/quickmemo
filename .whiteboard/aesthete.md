# Aesthete分析: 音声入力の使い勝手向上

## サマリー（3行以内）

音声録音中のユーザー体験は「不安」が支配的。テキスト重複で「壊れている」印象、停止ボタンの無反応で「コントロールを失った」感覚、安定性の低さで「いつ止まるかわからない」不安。
追記モードは「存在に気づけない機能」という UX の致命的問題を抱えており、発見性の改善は単なるラベル追加ではなく、ユーザーの行動導線全体の設計が必要。
修正後の体験は「安心して使える → 便利さに気づく → 習慣化する」という段階的な信頼構築のストーリーになるべき。

## 提案一覧

### [P-01] 停止ボタンの即時フィードバック: 「押した瞬間」の安心感
- **深刻度**: Critical
- **分類**: UX
- **問題**: ユーザーが停止ボタンをタップした瞬間、何も起きない。pulse アニメーションは続き、「Recording...」ラベルも変わらない。ユーザーは「ちゃんと押せたのか？」と不安になり、連打する可能性がある。これは操作の基本原則「即時フィードバック」の違反。
- **提案**:
  1. 停止ボタンタップ直後（`stopVoiceMemo()` 内の冒頭）で以下を即座に実行:
     - pulse アニメーションを停止（赤丸を灰色に変更、またはフェードアウト）
     - ステータスラベルを「処理中...」に変更
     - 停止ボタン自体を即座に非活性化（二重タップ防止 + 視覚的フィードバック）
  2. 新規メモモードの場合は「要約中...」のスピナーを即座に表示
  3. 追記モードの場合は「保存中...」を一瞬表示してからオーバーレイを閉じる
- **実装コスト**: S (~15行: JS) + S (~10行: CSS)
- **リスク**: 低。UI 状態の即時変更は非同期処理に影響しない。
- **根拠**: `app.js:1562-1567` (stopVoiceMemo), `style.css:464-475` (pulse animation)

### [P-02] テキスト重複の視覚的影響: 信頼感の喪失
- **深刻度**: Critical
- **分類**: UX
- **問題**: 録音中のトランスクリプト表示で同じテキストが繰り返されると、ユーザーは「アプリが壊れている」と即座に判断する。これは単なるバグではなく、アプリ全体への信頼を損なう体験。特に音声入力という「不安な操作」（マイクに向かって話す行為自体がストレス）において、表示の正確性は安心感の基盤。
- **提案**: 技術的な dedup 修正（Pragmatist の領域）に加えて、表示側でも防御:
  1. `renderTranscript()` で表示前に最終チェック: 直前の表示内容と同一なら DOM 更新をスキップ
  2. 新しいセグメントが追加された際に、短いフェードイン（opacity 0→1, 200ms）で「新しいテキストが追加された」ことを視覚的に示す
  3. 最新のセグメントにはわずかなハイライト背景（500ms で消える）を付けて、ユーザーが「今どこまで認識されたか」を直感的に把握できるようにする
- **実装コスト**: M (~25行: JS + CSS)
- **リスク**: アニメーションが頻繁すぎると逆に煩わしい。セグメント追加頻度（数秒に1回程度）なら許容範囲。
- **根拠**: `app.js:1540-1560` (renderTranscript), `style.css:490-507` (transcript styles)

### [P-03] 録音中の「生存感」: ユーザーを安心させる継続的フィードバック
- **深刻度**: High
- **分類**: UX
- **問題**: 現在の録音中 UI は pulse アニメーションと「Recording...」ラベルのみ。沈黙が続くと「まだ動いているのか？」という不安が高まる。特に auto-restart のタイミングでは一瞬フリーズしたように見える可能性がある。
- **提案**:
  1. 録音経過時間のカウンター表示（00:00 形式）: 数字が動き続けることで「生きている」ことを示す
  2. auto-restart 時に pulse が途切れないよう、アニメーションは CSS で継続させ、JS の再起動に依存しない設計にする
  3. 沈黙が5秒以上続いた場合、ラベルを「聞き取り中...」に変更して「待機中である」ことを明示する
- **実装コスト**: M (~30行: JS for timer + CSS)
- **リスク**: タイマー表示は `setInterval` で実装するが、オーバーレイ非表示時にクリアし忘れるとリークする。`cancelVoiceMemo` と `processVoiceResult` の両方でクリア必須。
- **根拠**: `app.js:1446` (status label), `style.css:464-475` (pulse), `index.html:65-68` (status area)

### [P-04] 追記モードの発見性: 行動導線の設計
- **深刻度**: High
- **分類**: UX
- **問題**: 追記ボタン（`voice-append-btn`）はエディタヘッダーの Back ボタンの直後に配置されているが、ピン・色・コピーと同じアイコンスタイルで視覚的に差別化されていない。ユーザーの視線はヘッダーの左端（Back）から右端（アクション群）に流れるが、マイクボタンは左寄りに孤立している。
- **提案**:
  1. **アイコンの差別化**: マイクアイコンに小さな「+」マークを重ねた合成アイコンにする（追記であることの視覚的手がかり）
  2. **初回利用ガイド**: 初めてエディタを開いた際に、マイクボタンの近くにツールチップ風の吹き出し「音声で追記できます」を表示し、タップまたは3秒経過で消える（localStorage で表示済みフラグ管理）
  3. **ボタンの色差別化**: 他のヘッダーアクションはモノクロだが、追記マイクボタンだけアクセントカラー（薄い青）のアウトラインを付けて目立たせる
  4. **title 属性**: `title="音声で追記"` を追加（長押し/ホバーでのヒント）
- **実装コスト**: M (~30行: HTML + CSS + JS for tooltip)
- **リスク**: 初回ツールチップは「うるさい」と感じるユーザーもいる。一度だけ・すぐ消えるなら許容範囲。ツールチップの実装が複雑になりすぎないよう、CSS-only または最小限の JS で実装する。
- **根拠**: `index.html:91-98` (voice-append-btn), `style.css` (header__action styles)

### [P-05] オーバーレイのモード表示: 追記モードの明示
- **深刻度**: Medium
- **分類**: UX
- **問題**: 追記モードで録音オーバーレイを開いた場合、「Appending...」というラベルは表示されるが、既存のコンテキスト表示（ノートタイトルの断片）は小さく目立たない。ユーザーは「今どのモードで録音しているか」を即座に判断できない。
- **提案**:
  1. 追記モードのオーバーレイでは、ステータスラベルのデザインを変える（例: アイコンを「マイク+矢印」にする、ラベル色をアクセントカラーにする）
  2. コンテキスト表示（対象ノート名）をより目立つサイズ・位置にする
  3. 新規メモモードとの視覚的区別を明確にする（例: オーバーレイ背景色の微妙な違い、ヘッダーバーの色）
- **実装コスト**: S (~15行: CSS)
- **リスク**: 低。CSS のみの変更。
- **根拠**: `app.js:1509` (Appending label), `index.html:64` (voice-context), `style.css:540-554` (context styles)

### [P-06] 録音完了後のトランジション: 自然な画面遷移
- **深刻度**: Medium
- **分類**: UX
- **問題**: 録音停止後、オーバーレイが即座に `hidden` になる（追記モード）、または要約完了後に瞬間的に消える（新規モード）。画面が「パッ」と切り替わり、ユーザーは一瞬方向感覚を失う。
- **提案**:
  1. オーバーレイを閉じる際に短いフェードアウト（200-300ms, opacity 1→0）を追加
  2. 新規メモの場合、フェードアウトの後にエディタがスライドインする流れを作る
  3. 追記モードの場合、テキストが追加された箇所がハイライトされてからフェードアウトする
- **実装コスト**: S (~15行: CSS transitions + JS class toggle)
- **リスク**: `hidden` 属性は `display: none` なのでトランジションが効かない。`opacity` と `pointer-events` ベースの非表示に切り替える必要がある。ただし既存の `.voice-overlay[hidden] { display: none; }` を変更する影響範囲を確認する必要あり。
- **根拠**: `style.css:425-438` (voice-overlay base + hidden), `app.js:1608` (overlay hidden = true)

# 実用主義分析: QuickMemo UX改善

## サマリー（3行以内）

アーカイブ一括削除がない点が最大の実用上の痛点。ドロップダウンメニューの拡張（Import JSON / Delete All Archived）で低コストに解消できる。
それ以外は「機能は揃っているが、あと一歩の導線最適化」が必要なフェーズ。検索・フィルタの欠如がメモ数増加時のボトルネックになる。

---

## 改善提案一覧（実装コスト順：低 -> 高）

### 1. アーカイブ一括削除 [報告済み課題への直接対応]

- **問題**: アーカイブが溜まると1件ずつスワイプ削除するしかない。10件あれば10回スワイプが必要。
- **改善案**: Archiveタブ表示時にヘッダーまたはリスト上部に「Delete All Archived」ボタンを追加。確認ダイアログ（`confirm()`で十分）の後、`data.notes = data.notes.filter(n => !n.archived)` で一括削除。Undo付きToastで全件復元可能にする。
  - 実装箇所: `app.js` の `renderList()` 末尾、またはドロップダウンメニューにArchiveタブ時のみ表示される項目を追加
  - 既存パターン: `deleteNote()` のUndo/Toast機構をそのまま再利用
  - 変更量: app.js +20行、index.html or app.js(DOM生成) +5行
- **実装コスト**: Small
- **ROI**: 極めて高い（報告済み課題を直接解決、最小コード変更）
- **優先度**: **High**

### 2. JSONインポート機能

- **問題**: Export JSONはあるがImportがない。バックアップの片道切符になっている。端末移行・復元ができない。
- **改善案**: ドロップダウンメニューに「Import JSON」を追加。`<input type="file" accept=".json">` を非表示で配置し、クリックで発火。読み込んだJSONを `data.notes` にマージ（IDの重複チェック付き）。
  - 実装箇所: ドロップダウンメニューに項目追加、`app.js` に `importData()` 関数追加
  - 既存パターン: `exportData()` の逆操作、`loadData()` のバリデーションロジック再利用
  - 変更量: app.js +35行、index.html +2行
- **実装コスト**: Small
- **ROI**: 高い（Export機能の価値を完成させる）
- **優先度**: **High**

### 3. localStorage容量の可視化と警告

- **問題**: `saveData()` で `catch` して "Storage full" とだけ表示するが、ユーザーが事前に容量を把握できない。満杯になってから焦る。
- **改善案**: Settingsに使用量表示を追加。`JSON.stringify(localStorage).length` でバイト数概算 → `(使用量 / 5MB) * 100` でパーセント表示。80%超で警告色。
  - 実装箇所: Settings画面に `<div>` 1つ追加、`openSettings()` で計算・表示
  - 変更量: app.js +10行、index.html +5行、style.css +10行
- **実装コスト**: Small
- **ROI**: 中程度（データロスの予防）
- **優先度**: **Medium**

### 4. エディタからの直接アーカイブ/削除

- **問題**: メモをアーカイブ・削除するにはリスト画面に戻ってスワイプする必要がある。エディタで「もういらない」と判断した時に即座に操作できない（画面遷移 + スワイプの2アクション必要）。
- **改善案**: エディタヘッダーに3点メニューを追加し、「Archive」「Delete」を配置。既存の `archiveNote()` / `deleteNote()` を呼んで `closeEditor()` すればよい。
  - 実装箇所: エディタヘッダーにドロップダウン追加（リスト画面の既存パターンを流用）
  - 既存パターン: `archiveNote()`, `deleteNote()`, ドロップダウンメニューUIの再利用
  - 変更量: app.js +25行、index.html +10行
- **実装コスト**: Small
- **ROI**: 高い（頻度の高い操作の導線短縮）
- **優先度**: **Medium**

### 5. リスト画面でのインクリメンタル検索

- **問題**: メモが30件を超えるとスクロールで探すのが非効率。色やピンでの分類はあるが、テキスト検索がない。
- **改善案**: ヘッダー下に検索バー追加（トグル表示）。`getFilteredNotes()` にフィルタ条件を追加し、`note.title + note.body` に対して `includes()` でマッチング。入力ごとにdebounce付きで `renderList()` を呼ぶ。
  - 実装箇所: `app.js` の `getFilteredNotes()` 拡張、検索バーUI追加
  - 既存パターン: タブ切り替え時の `renderList()` パターンを流用
  - 変更量: app.js +30行、index.html +5行、style.css +15行
- **実装コスト**: Medium
- **ROI**: 高い（メモ数増加時のUX劣化を防ぐ）
- **優先度**: **Medium**

### 6. コピーボタンの対象テキスト改善

- **問題**: リストのコピーボタンは `note.body` のみコピーする（`app.js` 442行目）。タイトルが別フィールドなので、タイトル付きメモの場合にタイトルがコピーに含まれない。エディタのコピーも `editorTextarea.value` のみ（1218行目）。
- **改善案**: コピー対象を `(note.title ? note.title + '\n' : '') + note.body` に変更。
  - 変更量: app.js 2行修正
- **実装コスト**: Small（2行変更）
- **ROI**: 中程度（地味だが正確さが向上）
- **優先度**: **Medium**

### 7. 色フィルタリング（カラータグによる絞り込み）

- **問題**: 色分け機能はあるが、特定色だけ見たい時のフィルタがない。ビジュアル分類はできても、絞り込みができない。
- **改善案**: タブバーの右端に色フィルタドット（現在のカラーピッカーUIを流用）を追加。タップで色トグル → `getFilteredNotes()` にフィルタ条件追加。
  - 既存パターン: カラーピッカーUIのドットをそのまま再利用
  - 変更量: app.js +25行、style.css +15行
- **実装コスト**: Medium
- **ROI**: 中程度（色分けの価値を完成させる）
- **優先度**: **Low**

### 8. スワイプ方向でアーカイブ/削除を分離（Archiveタブ限定）

- **問題**: Archiveタブでは左スワイプ=永久削除のみ。復元ボタンはあるが、スワイプの一方向しか活用されていない。ただし右スワイプはChrome戻るジェスチャーと競合するリスクがあり、PLAN-v2でも明確に却下されている。
- **改善案**: 実装しない。復元ボタン方式が既にあり、ジェスチャー競合リスクを考えると現状維持が正解。
- **実装コスト**: N/A
- **ROI**: N/A
- **優先度**: **見送り**

### 2. 頻度 vs 手間のミスマッチ

**手間が過大な高頻度操作:**
- アーカイブの一括掃除: 溜まったらまとめて消したいのに1件ずつ → 提案#1で解決
- エディタ内でのメモ破棄: 書いてる途中で「いらない」→ 一旦戻ってスワイプ → 提案#4で解決

**UIが目立ちすぎる低頻度操作:**
- Voice FAB: 常時2つのFABが画面下部を占有。Gemini APIキー未設定なら使えない機能がFABを専有している。
  - ただし、「1タップで音声入力開始」という導線の速さは価値がある。APIキー未設定時に非表示にする程度が妥当。
- Settings: ドロップダウンの中にあり、適切な深さ。問題なし。

**手軽さが適切な高頻度操作:**
- コピー: リストから1タップ。優秀。
- 新規作成: FAB 1タップ。優秀。

### 3. 既存機能の再利用・拡張

**流用可能な既存パターン:**

| 既存パターン | 流用先 | 変更量 |
|---|---|---|
| `deleteNote()` のUndo Toast | 一括削除のUndo | +15行 |
| `exportData()` のJSON処理 | Import機能 | +35行 |
| ドロップダウンメニューUI | エディタ内メニュー | +20行 |
| `getFilteredNotes()` のフィルタ | 検索・色フィルタ | +20行 |
| カラーピッカーUIの `.color-dot` | 色フィルタUI | +15行(CSS) |

**app.js のコード構造は拡張しやすい**: 関数が独立しており、グローバルステートへのアクセスが明示的。新機能追加時にリファクタ不要。

### 4. 不要な複雑さ

**過剰ではない点（適切な設計）:**
- スワイプアニメーション: touch系イベントの手動処理は必要。ライブラリ不使用で正解。
- SVGアイコンの手動生成（`createElementNS`）: 外部依存なしのPWAとして妥当。冗長だが機能的。
- History API統合: PWAのUXとして必須。

**やや冗長だが問題ではない点:**
- SVGアイコン生成コード（ピンアイコン: 338-358行、復元アイコン: 390-406行、コピーアイコン: 419-438行）: 各20行程度。SVGスプライトやテンプレート関数にまとめれば短くなるが、動作に影響しないので低優先。

**実質的に不要な複雑さ: なし。** バニラJS + 1400行で、過剰な抽象化やレイヤー分離はない。実用的。

### 5. バッチ操作

**現在のバッチ操作: ゼロ。** 全操作が単一アイテム対象。

**必要なバッチ操作（優先順）:**

1. **アーカイブ一括削除**（提案#1）: 報告済み課題。最優先。
2. **複数選択 → 一括アーカイブ/削除/色変更**: 将来的にはあると便利だが、実装コストが大きい（選択モードUI、チェックボックス、一括操作バー）。メモアプリの利用パターンとして「溜まったアーカイブを掃除する」が圧倒的に多いので、提案#1だけで80%のニーズは満たせる。
   - 複数選択UIは **見送り** を推奨（コスト大、効果限定的）

### 6. データ管理

**現状の課題:**

| 項目 | 状態 | 対応 |
|---|---|---|
| Export | あり（JSON） | 正常動作 |
| Import | **なし** | 提案#2で対応 |
| 容量管理 | **なし**（満杯時エラーのみ） | 提案#3で対応 |
| バックアップ自動化 | なし | PWAの制約上、手動Exportが現実的。自動化は過剰 |
| データ形式バージョニング | version:1 固定 | 現時点で十分。フィールド追加はundefined許容で後方互換 |

**localStorageの制約:**
- 上限: 約5MB（ブラウザ依存）
- テキストメモなら数千件は保存可能（1件 500bytes として ~10,000件）
- 容量問題は現実的にはかなり先だが、可視化があると安心感がある
